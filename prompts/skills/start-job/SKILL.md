# L 작업 절차 (start-job)

`HEAD_CORE`의 판정으로 **L**이 된 작업(처음부터 L이거나 S 진행 중 L로 올라간 작업)에서 이 절차를 순서대로 따른다. 요구가 아직 기획 수준이면 `cortex_prompt(kind: "skill", name: "product-planning")`을 먼저 수행하고, 개발 작업이면 `cortex_prompt(kind: "standard", name: "DEVELOPMENT_STANDARD")`를 기준으로 삼는다.

## 1. L 선언

- 왜 L인지(해당 기준)를 사용자에게 한 줄로 알린다.
- L에서 HEAD가 하는 일은 계약 쓰기, 결과 확인, 판정이며, 코드는 워커가 고친다.

## 2. 탐색이 필요한 경우 — 조사와 구현 분리

고칠 위치와 이유를 지금 말할 수 없을 때는 조사와 구현을 나누어 순서대로 진행한다.

- **무엇을 찾을지 정해진 조사**(예: 특정 함수를 부르는 곳 전부 찾기)는 `researcher` 워커 하나에게 맡긴다.
- **무엇이 나올지 모르는 탐색**(예: 원인을 모르는 오동작)은 같은 물음을 **`researcher` 워커 여럿(가능하면 서로 다른 모델)**에게 따로 맡긴다. 지시에는 증상, 재현 방법, 볼 범위만 적고, HEAD가 미리 생각한 원인이나 해결안은 적지 않는다(적으면 워커가 그것을 확인해 줄 뿐이다).
- 조사 결과는 항목마다 근거 위치(`파일:줄`, 실행한 명령과 출력)를 달아 받는다. HEAD가 그 위치의 원본을 직접 읽어 대조하고, 워커들의 결과가 갈리는 곳을 판단해 원인과 고칠 위치를 확정한다.
- 원인이 확정된 뒤에야 구현을 맡긴다. 구현 워커(`developer`)에게는 확정된 원인과 고칠 위치를 주고 구현과 실행 증명만 맡긴다.

## 3. 실행 형태 고르기

- **경계가 정해진 작업 하나**: `cortex_prompt(kind: "skill", name: "delegate")`를 읽어 맡긴다. 확정된 명세를 그대로 옮기면 `coder`, 경계 안에서 설계 재량이 필요하면 `developer`를 고른다.
- **여러 사이클에 걸친 작업**: `cortex_prompt(kind: "skill", name: "plan-run")`을 읽어 `P0` 기준선을 세우고 진행한다.
- **동시 실행**: 고칠 파일이 서로 겹치지 않는 작업은 워커를 동시에 띄워도 된다.

## 4. 워커를 띄우는 방법 세 가지

작업 성격과 모델 분리 필요에 따라 아래 세 방법 중 하나를 쓴다.

- **호스트의 서브에이전트**: 현재 호스트의 서브에이전트 도구로 새 컨텍스트 워커를 띄운다.
- **`cortex-worker` 명령(다른 모델을 헤드리스로 실행)**: 지시는 파일로 써서 `--brief`로 넘기고, 결과 파일이 필요하면 `--out`을 지정해 실행한다(PowerShell에서는 `cortex-worker`로도 실행된다).
  ```powershell
  node --no-warnings {{HERDR_CORTEX_ROOT}}/scripts/cortex-worker.mjs --role <역할> --agent <antigravity|claude> --model <모델> --brief <지시 파일> [--out <결과 파일>] [--timeout <분>] [--allow <허용 규칙>]... [--cwd <폴더>]
  ```
  헤드리스 워커는 실행 중 권한을 물어볼 수 없으므로 필요한 명령·도구를 `--allow`로 미리 허용하고, 무엇을 허용했는지 사용자에게 알린다.
- **다른 Herdr 탭**: `relay_tabs`로 유휴 탭을 확인하고 `relay_send`로 지시와 기준선 문서를 전달한다.

## 5. 결과 받기

- 워커의 보고를 그대로 믿지 않고, 실행 증명(실행한 명령과 실제 출력)을 직접 확인한다.
- 핵심 수치는 HEAD가 직접 한 번 돌려 본다.

## 6. 독립 검수

- 만든 워커와 다른 새 컨텍스트(가능하면 다른 모델)의 `reviewer`에게 `cortex_prompt(kind: "skill", name: "independent-review")` 절차로 맡긴다.
- `NEEDS_FIX`면 수정 방향을 HEAD가 정해 다시 위임하고 새 컨텍스트에서 다시 검수받는다. 같은 지적이 두 번 되풀이되면 세부를 덧대지 않고 원래 문제로 올라간다.
- 검수자가 짚은 작은 수정이 S 기준에 들면 HEAD가 직접 고치고 실행해 확인해도 된다.

## 7. 마무리

- 독립 검수 `ACCEPT`와 `memory_save`(무엇을 했는지, 검수 결과, 남은 미확인 사항) **둘 다** 끝나야 L 작업이 끝난다.
- 탭의 **L** 상태는 훅에 기록되며, 독립 검수 `ACCEPT`와 `memory_save` 두 조건이 차면 **S**로 풀린다.
- 커밋은 사용자가 정한 방침을 따르고, 방침이 없으면 묻는다.
