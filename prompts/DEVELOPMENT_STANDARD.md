# 개발 기준 (DEVELOPMENT_STANDARD)

소프트웨어 기획·구현·리뷰 시 HEAD와 `developer`가 공통으로 적용하는 7원칙이다.
프로젝트 고유 규약은 저장소 설정과 기존 코드가 제공하고, 의사결정 권한은 각 역할 문서가 규정한다.
`coder`는 이 기준을 자율 설계 근거로 사용하지 않으며, 명세 작성자가 이 기준을 적용해 확정한 규격을 충실히 번역한다.

## 1. 필요한 동작만 구현한다

- 요청된 동작과 유지되어야 할 기존 계약에서 범위를 정의한다.
- 관련 기존 구현을 먼저 읽고, 필요한 책임을 이미 수행하며 현재 변경에 맞는 코드를 우선 재사용한다.
- 기존 패턴은 재사용 후보로 검토하되 무조건 복제하지 않는다. 요구사항이나 본 기준과 본질적으로 충돌하면 임의로 주변을 재설계하지 않고 충돌 사실을 상위에 보고한다.
- 옵션, 확장 장치, 관리 기능, 중간 상태는 현재 요구사항이 필요로 할 때만 추가하고 무관한 개선은 변경 범위 밖에 둔다.
- 모든 추가 요소에 대해 "이것이 없으면 어떤 요구 동작이나 보장이 깨지는가"를 설명할 수 있어야 한다.

## 2. 필요한 책임을 분리한다

- 실제로 구분되는 책임을 독립적으로 이해하고 변경할 수 있는 단위로 나눈다.
- 각 단위의 입력·출력·상태 변경을 명확히 하여 호출자가 내부 구현을 알지 않고도 사용할 수 있게 한다.
- 오케스트레이션 코드에서는 주 처리 단계와 실행 순서가 한눈에 드러나게 유지한다.
- 동일한 비즈니스 규칙 판단을 여러 곳에 중복 분산하지 않고 명확한 소유자를 둔다.
- 경계 분리는 책임이나 의존성 방향을 분명히 할 때만 도입하며, 호출 단계만 늘리는 빈 계층은 두지 않는다.
- 단순함은 최소 파일 수를 뜻하지 않는다. 지금 필요한 책임 분리와 막연한 미래 대비 추상화를 구분한다.

## 3. 책임이 있는 경계에서 검증한다

- 각 경계가 소유한 외부 입력, 권한, 비즈니스 상태 조건을 해당 경계에서 검증한다.
- 앞선 경계·타입·계약·DB 제약이 이미 보장한 조건은 재사용하고, 추가 책임이나 새로운 신뢰 경계·상태 전이가 있을 때만 재검증한다.
- 모든 검증에 대해 무엇을 보호하며 왜 그 위치에 있어야 하는지 설명할 수 있어야 한다.
- 확립된 실패 경계를 따르고, 폴백·재시도·복구 로직은 요구된 실패 동작에 필요할 때만 추가한다.

## 4. 보호할 동작에 맞춰 검증을 선택한다

- 권위 있는 실제 입력부터 결과가 소비되는 지점까지 대표 실행 경로를 실제 환경에서 검증한다.
- 테스트는 변경된 동작, 직접 연관된 회귀, 핵심 불변 조건을 보호하도록 선택한다.
- 기존 테스트나 대표 실행으로 충분한 보장이 확보되면 같은 보장을 중복하는 테스트를 추가하지 않는다.
- 새 함수·분기·헬퍼마다 기계적으로 테스트를 늘리지 않는다. 테스트 개수나 커버리지 수치는 목표가 아니다.
- 필요한 동작이 이미 충분히 검증되었다면 새 테스트를 추가하지 않는 것도 정상적인 선택이다.
- 계획은 검증할 동작과 테스트 추가·수정·실행 범위를 명시하며, 구현 워커는 임의로 범위를 확장하지 않는다. 관측 결과 현재 범위로 부족하면 부족한 보장과 사실을 계획 소유자에게 반환한다.

## 5. 영속 상태는 의미와 소유권으로 설계한다

- 테이블·컬럼·파일·저장 상태를 추가하기 전 기존 저장 데이터와 비교한다.
- 정본(authoritative) 데이터와 파생 값을 구분한다. 파생 값의 별도 저장은 현재의 정확성·이력·성능 등 명시적 요구가 있을 때만 허용한다.
- 누가 데이터를 생성·갱신하고 언제 폐기하는지 소유권을 명시해 여러 경로가 같은 사실을 제각각 확정하지 않게 한다.
- 모듈 분리만으로 새 저장소나 복제본을 만들지 않으며, 반대로 의미와 생명주기가 다른 데이터를 테이블 수 절감만으로 합치지 않는다.
- 변경 후에도 독자가 주 흐름, 정본 데이터, 상태 확정 지점을 추적할 수 있어야 한다.

## 6. 동작 변경 결정은 사전에 계획하고 합의한다

작업 기록에는 해당 변경에 필요한 항목만 간결히 담는다.

1. 필요한 동작과 범위 외 항목
2. 재사용할 기존 구현, 신규 동작의 소유자, 주요 연결 지점
3. 추가·변경되는 데이터·계약·의존성과 선택 이유(실질적으로 다른 대안 포함)
4. 대표 실행 경로와 선택된 테스트 범위
5. 사용자가 결정해야 할 사항

합의된 경계 내부의 식별자·함수/파일 분할·내부 알고리즘은 구현 소유자에게 맡긴다.
데이터 의미, 외부 계약, 주요 소유권 경계, 권한, 과금/핵심 정책, 주요 외부 의존성 변경 및 신규 영속 상태 도입은 구현 전 합의를 거친다.
실패나 동시성이 무결성·권한·정합성에 영향을 주는 변경은 실행 순서와 원자성 경계를 명시한다. 작은 변경은 짧게 유지하고 형식을 채우기 위해 가상 대안이나 리스크를 지어내지 않는다.

## 7. 같은 기준으로 리뷰한다

- 기존 동작에 대한 주장을 실제 코드 및 확정 요구사항과 대조한다.
- 누락된 요구사항과 불필요한 동작·상태를 점검한다.
- 필요한 책임이 적절히 분리되어 있고 연결 구조가 읽기 쉬운지 확인한다.
- 검증과 테스트가 실제로 무엇을 보호하며 변경 규모에 비례하는지 살핀다.
- 결함이 없으면 발견 사항 없음(`Clean Evaluation`)이 정상 결과다. 독자적인 이상적 아키텍처나 억지 지적 개수를 목표로 삼지 않는다.
